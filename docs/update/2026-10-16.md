## 图片引用生成与清理只认主目录文件

### 需求描述
生成图片引用方法时，只处理主目录（非变体目录）下的图片；清理失效引用时，也只检查主目录文件是否存在。变体目录（`1.5x`、`2.0x`、`3.0x`、`4.0x` 等）下的图片不单独生成引用，也不作为保留引用的依据——主目录的文件被删了，即使变体还在，对应的 getter 也会被剔除。

### 实现细节
- `collectImages()` 改为跳过变体目录：递归扫描时用 `/^\d+(\.\d+)?x$/` 正则匹配目录名，是变体目录就 `continue` 跳过，不再进入扫描。返回的数组直接收集主目录的图片路径，不再用 Map 做去重合并。
- `pruneMissingReferences()` 改为只检查主目录文件：用 `fs.existsSync(imagePath)` 直接判断 getter 记录的路径在磁盘上是否存在，不再调用 `areAllVariantsDeleted()` 检查变体。主目录文件不存在即视为失效，剔除该 getter。
- **`doGenerateForSingleImage()` 增加变体目录检查**：计算相对路径后，用 `path.sep` 拆分成数组，用 `.some()` 检查是否有任何一段匹配 `/^\d+(\.\d+)?x$/`，只要路径中任何层级包含变体目录就直接返回并记日志，不生成引用。这确保监听器捕获到深层变体目录下图片创建事件时（如 `assets/images/2.0x/icons/logo.png`）不会误生成 getter。
- 效果：`Images` 类里只会生成主目录图片的 getter；删除主目录图片后，即使变体目录还有同名文件，清理操作也会把对应的 getter 移除。

## 修复 pubspec.yaml 写入时数据位置打乱和注释丢失

### 问题描述
使用 `PubspecUtils` 修改 `pubspec.yaml` 的 `flutter.assets` 部分时，会将整个文件重新序列化，导致：
1. **数据位置被打乱** - YAML 库按自己的规则重新排序所有键
2. **注释全部丢失** - YAML 解析器不保留任何注释信息

这影响了用户的阅读体验和版本控制时的 diff 清晰度。

### 原因分析
原实现使用 `yaml` 库的 `parse()` + `stringify()` 组合：
```typescript
const content = fs.readFileSync(pubspecPath, "utf-8");
const data = parse(content);  // 解析为对象，丢失注释
// ... 修改 data.flutter.assets ...
fs.writeFileSync(pubspecPath, stringify(data));  // 重新序列化，顺序重排
```
这种方式会完全重写整个文件，无法保留原始格式和注释。

### 实现细节
改为**精确文本替换**策略，只修改 `flutter.assets` 部分：

1. **新增 `writePubspecAssetsOnly()` 方法**：
   - 读取原始文件内容（保留所有注释和格式）
   - 检测 `flutter:` 键的缩进级别（支持 2/4 空格等不同风格）
   - 构建新的 `assets:` YAML 块（保持与原有缩进一致）
   - 使用正则表达式匹配并替换现有的 `assets:` 部分
   - 若无 `assets:` 则插入到 `flutter:` 下方
   - 若连 `flutter:` 都没有则在文件末尾追加整个块

2. **移除对 `stringify` 的依赖**：
   ```typescript
   import { parse } from "yaml";  // 只保留 parse 用于读取
   // stringify 已不再需要
   ```

3. **辅助方法**：
   - `serializeAssets(assets, indent)`：将 assets 数组序列化为指定缩进的 YAML 字符串
   - `detectFlutterIndent(content)`：从原始内容中提取 `flutter:` 的缩进空格数

4. **调用点更新**：
   - `ensureAssetDirectory()` → 改用 `writePubspecAssetsOnly()`
   - `removeAssetDirectory()` → 改用 `writePubspecAssetsOnly()`
   - `syncAssetDirectories()` → 改用 `writePubspecAssetsOnly()`

5. **保留 `setAssets()` 方法**：
   - 仍用于内存中的对象操作（如其他代码可能需要访问 `pubspec.flutter.assets`）
   - 添加注释说明其用途限制

### 效果对比
修改前：
```yaml
# 项目配置
name: my_app
version: 1.0.0

# Flutter 相关配置
flutter:
  # 资源文件列表
  assets:
    - assets/images/
    - assets/fonts/
```

修改后（添加 `assets/icons/`）：
```yaml
# 项目配置
name: my_app
version: 1.0.0

# Flutter 相关配置
flutter:
  # 资源文件列表
  assets:
    - assets/images/
    - assets/fonts/
    - assets/icons/  # ✅ 只添加了这一行，其他内容和注释保持不变
```

- 手动测试：在包含多段注释的 `pubspec.yaml` 中添加/删除 assets 目录
- 确认只有 `assets:` 部分被修改，其他配置（name、version、dependencies 等）位置和注释均保持不变
- 确认缩进级别自动适配（2 空格、4 空格等不同风格都能正确处理）

## 修复 executeFormatDocumentProvider 拿不到 Dart 格式化结果

### 问题描述
调用 `ForamtUtils.formatDocument()` 时，`vscode.executeFormatDocumentProvider` 返回空数组或 undefined，导致生成的 Dart 代码没有被格式化。

### 原因分析
`vscode.executeFormatDocumentProvider` 命令有以下依赖条件：
1. **文档必须已在编辑器中打开** - Dart 扩展只有在文档打开时才会注册 DocumentFormattingEditProvider
2. **语言服务完全就绪** - 文档打开后需要时间让 Dart 扩展激活并注册提供者
3. **文件系统写入不等于打开** - `vscode.workspace.fs.writeFile()` 只是写文件到磁盘，不会触发文档打开事件

原代码的执行顺序和方式存在问题：
```typescript
await vscode.workspace.fs.writeFile(uri, Buffer.from(content, "utf-8"));
await ForamtUtils.formatDocument(uri); // ❌ 此时文档未打开
const doc = await vscode.workspace.openTextDocument(uri);
```

即使调整为先打开文档，`openTextDocument` 只加载文档到内存但不显示在编辑器中，Dart 扩展可能仍未完全激活其格式化提供者。

### 实现细节
采用多重保障措施：

1. **使用 `showTextDocument` 而非 `openTextDocument`**（`image-reference-generator.ts`）：
   ```typescript
   const editor = await vscode.window.showTextDocument(uri, { preview: true });
   await new Promise(resolve => setTimeout(resolve, 100)); // 等待语言服务就绪
   await ForamtUtils.formatDocument(uri);
   ```
   `showTextDocument` 会在编辑器中真正显示文档，触发 Dart 扩展的完整激活流程。

2. **添加调试日志**（`format-utils.ts`）：
   - 检查文档是否已打开
   - 记录文档语言模式
   - 输出格式化结果数量

3. **备选方案：直接调用 `dart format` 命令**（`format-utils.ts`）：
   当 `executeFormatDocumentProvider` 返回空结果时，自动降级为执行系统命令：
   ```typescript
   cp.spawnSync("dart", ["format", filePath])
   ```
   这样即使 VS Code 的语言服务有问题，也能保证代码被正确格式化。

- `src/utils/format-utils.ts` (修改)

## 移除图片引用前先剔除所有失效引用

### 需求描述
`ImageReferenceGenerator` 增加一个「剔除所有指向已不存在图片的引用」的方法，并在每次移除图片数据之前先执行它。这样除了本次要删的那张图，历史遗留的失效 getter（手工删除图片、监听器漏事件、变体判定收紧后失效的旧条目）也会被顺带清掉，`Images` 类不会长期残留死引用。

### 实现细节
- 新增私有 `pruneMissingReferences(workspaceRoot, content)`：用 `/\s*static\s+String\s+get\s+(\w+)\s*=>\s*'([^']*)';\n?/g` 遍历类文件内容，把 getter 里记录的资源路径拼上项目根目录做存在性判断，返回 `{ content, removed }`（`removed` 为被剔除的方法名）。
- 存在性判断复用 `areAllVariantsDeleted()` → `ImageVariantUtils.collectVariants()`：基准目录或其直接变体子目录下仍有同名同扩展名的文件，就认为引用有效。由于记录的路径已去掉变体目录（如 `assets/images/icons/only2x.png`），只有变体时引用同样保住。
- 调用点放在 `doRemoveReference()` 开头，即「移除图片数据前」；因此它天然处在串行队列内部，不需要单独排队，也没有嵌套 `enqueue` 死锁风险。清理与本次目标删除任一有变化都写回文件。
- 无变化时不写盘、不刷格式化，保持幂等。
- 剔除数量通过 `Logger.showNotification` 提示，逐条走 `Logger.d`。
- 该逻辑只在真正进入移除流程时执行：`removeReferenceIfAllVariantsDeleted()` 在「还有变体存活」时提前返回，不做清理。若希望这种分支也顺带清理，在该分支补一次 `pruneMissingReferences` 即可（未做，等待确认）。
- **写入后自动格式化**：`writeImagesClassContent()` 在写盘后打开文档，调用 `vscode.executeFormatDocumentProvider` 对整份 Dart 文件进行格式化（空格缩进、tabSize=2），再保存，保证生成的代码符合项目风格。

### 顺带修正一条文档描述
「一键删除选中的单个或多个图片及其所有变体」一节原先写着「只删 `foo.png` 时检测到 `foo.webp` 仍在，引用方法会被保留」。这个结论在变体判定收紧为「同名且同扩展名」之后就不成立了：`foo.png` 的所有变体消失 → 进入移除流程 → getter 名忽略扩展名（`foo.png` 与 `foo.webp` 共用 `fooBar`），记录路径又是 `foo.png`，于是共用 getter 会被删掉。该条描述已按实际行为改写。

### 验证

- D 只删 `pair.png`（`pair.webp` 仍在）→ 共用 getter 被移除，即上面修正文档时描述的实际行为。

## pubspec.yaml 写入前清理失效的图片资源目录

### 需求描述
`ensureAssetDirectory` / `removeAssetDirectory` 在插入或移除条目前，先检查 assets 中已记录的目录在磁盘上是否还存在，不存在则一并移除，避免残留失效条目导致 `flutter pub get` / 构建报「asset not found」。

清理范围按确认只覆盖 `imageSrcPath` 前缀下的条目（如 `assets/images/`）；其它资源（字体、`assets/data` 等用户手工维护的条目）即使目录不存在也原样保留，不由插件删除。

### 实现细节
- 新增私有方法 `pruneMissingImageAssets(workspaceRoot, assets)`：按前缀过滤出图片资源条目，去掉结尾斜杠后用 `fs.existsSync` 判断存在性，不存在则剔除并记日志；返回 `{ assets, changed }`。前缀由 `getImageAssetPrefix()` 从 `ConfigUtils.imageSrcPath` 推导，未配置时不清理。`imageSrcPath` 自身那条（如 `assets/images`）不在清理范围内。
- `ensureAssetDirectory`：先清理再判断是否已存在。新增与否都可能在清理后为空操作，因此用 `added || pruned.changed` 决定是否写文件——只有两者都没有变化时才返回 `false` 并完全不落盘。
- `removeAssetDirectory`：同上。待删目录通常已经被删掉，清理会先把它剔除，此时显式 `splice` 找不到条目但 `pruned.changed` 为真，仍会正确落盘；对非图片前缀的条目则仍走显式移除。
- `syncAssetDirectories`：移除失效条目改用同一个清理方法。

### 顺带修掉的一个问题
`syncAssetDirectories` 原先只枚举 `imageSrcPath` 的**一级**子目录，再把「前缀匹配且不在一级列表里」的条目全部删除。而监听器会把多级子目录（如 `assets/images/icons/nested`）写进 assets，于是配置变更触发 `reinitialize` 时，这些**磁盘上仍然存在**的深层条目会被误删且不会补回。改为按存在性判断后，深层条目得以保留。

### 追加：syncAssetDirectories 改为递归所有层级
上一条里「只认一级子目录」的疑问已明确改掉：`syncAssetDirectories` 不再只枚举 `imageSrcPath` 的直接子目录，而是递归收集所有层级。

- 新增私有 `collectSubDirectories(workspaceRoot, directoryPath, out)`，深度优先收集所有层级的子目录，输出相对于项目根目录的 Unix 风格路径；`readdirSync` 失败只记日志并跳过该层，不让整个同步崩掉。
- 跳过以 `.` 开头的隐藏目录（`.git`、`.DS_Store` 之类），与监听器里 `startsWith(".")` 的判断保持一致。
- 变体目录（`1.5x`、`2.0x` 等）按普通子目录一并写入 assets，Flutter 解析倍图时需要这些条目。
- `imageSrcPath` 自身那条（如 `assets/images`）仍不由 sync 添加或删除，用户手写的会保留。

### 验证
用 esbuild 把 `pubspec-utils.ts` 打成 CJS、以桩替换 `vscode`（只需 `workspace.getConfiguration`，`Logger` 本身是空操作），对真实函数跑了两轮断言：

- 清理相关（12 条）：清理只作用于图片前缀、带结尾斜杠的条目、深层条目保留、`ensure` 幂等时不改写文件、`remove` 对已消失目录仍落盘、并发两个 `ensure` 互不覆盖。
- 递归同步（5 条）：多层目录（`icons/nested/deep`）全部收齐、隐藏目录被跳过、变体目录 `2.0x` 正常收录、重复执行不改写文件、`imageSrcPath` 整体缺失时只清图片条目、`ensure` + `sync` 组合不产生重复条目。

全部通过，临时文件已删除。

## images.dart 的写操作串行化

### 需求描述
承接上一条的「已知遗留」：`ImageReferenceGenerator` 对 `images.dart` 的读-改-写原先靠监听器里 300ms 延时近似排序，批量删除/重命名时仍会丢更新。现按 `PubspecUtils` 的做法加同样的串行队列。

### 实现细节
- 新增静态 `opQueue` + `enqueue()`，与 `PubspecUtils` 同一套：任务链在队尾执行，单个任务失败时队列吞掉 rejection 继续跑后续任务，错误仍通过返回的 Promise 抛给调用方。
- **队列必须是静态的**：监听器每次事件都 `new ImageReferenceGenerator(...)`，实例级队列无法跨事件串行。
- 拆成「公开排队方法 + 私有 `doXxx` 实现」：`generateForDirectory` / `generateForSingleImage` / `removeReference` / `regenerateForDirectory` / `removeReferenceIfAllVariantsDeleted` 对外只负责入队，实体逻辑挪到 `doGenerateForDirectory` 等私有方法。
- 原因是**嵌套入队会自我等待**：`doRegenerateForDirectory` 内部改调 `doGenerateForDirectory`，`removeReferenceIfAllVariantsDeleted` 内部改调 `doRemoveReference`；若排队任务里再调用公开的排队方法，内层任务被挂到外层任务的 Promise 之后，外层又在等内层，直接死锁（已用脚本验证：嵌套 `enqueue` 不会 resolve）。
- 监听器侧：`handleImageDeleted()` 里的 300ms `setTimeout` 已删除，排序责任交给队列；注释同步改为说明「事件先后顺序不保证，但队列保证后一个任务读到的是前一个写完后的内容」。

## 修正图片变体判定与重命名时的引用删除

### 问题描述
`ImageReferenceGenerator` 早前的变体判定是自己写的一套：全树递归扫描 `imageSrcPath`，并把扩展名剥掉后比对路径。两处都有问题：

1. 剥掉扩展名后，`foo.png` 与 `foo.webp` 会被当成同一张图，只删其一另一张会"保住"引用，与项目既定规则（图片身份包含扩展名，变体按**同名且同扩展名**匹配）相矛盾。
2. 全树递归扫描比 Flutter 约定的范围（基准目录 + 其直接变体子目录）宽得多，既慢又可能命中无关目录下的同名文件。

另外，`ImageAssetWatcher` 里用 `pendingDeleteTimeouts: Map<相对路径, Timeout>` 想实现"删除后 300ms 内若出现同路径 create 就判定为重命名并取消删除"。重命名时 delete 带旧路径、create 带新路径，两个 key 永远对不上，这个取消分支实际不会命中；而且 `removeReferenceIfAllVariantsDeleted` 本身已能保证正确性（只要还有任一变体存活就不移除引用），延迟判定重命名是多余的。

### 实现细节
- 变体判定改为复用 `ImageVariantUtils.collectVariants(imageFilePath)`：它按 Flutter 约定只看基准目录及其直接变体子目录，并按完整文件名匹配。`areAllVariantsDeleted()` 收敛为其一行 `collectVariants(path).length === 0`，删除 `findVariantFiles()` 递归实现。
- 删除 `pendingDeleteTimeouts` 字段与两处 Map 操作；图片删除改由 `handleImageDeleted()` 处理。
- 保留 300ms 等待，但原因不再是"识别重命名"：VS Code 把 rename 拆成「旧路径 delete + 新路径 create」两次事件，若立刻处理删除，`removeReference` 会读到 create 写入前的旧内容，写回时覆盖掉刚新增的 getter。注释按此重写。
- 顺带清理创建分支里一行无用赋值（`let uri2 = ...`）。

### 已知遗留
`images.dart` 的读-改-写当时仍靠 300ms 延时排序，并非真正串行；批量删除/重命名可能出现更新丢失。
（已由「images.dart 的写操作串行化」一条解决，监听器里的延时已移除。）

## 修复 pubspec.yaml 并发读写导致的更新丢失

### 问题描述
`PubspecUtils` 的 `ensureAssetDirectory` / `removeAssetDirectory` / `syncAssetDirectories` 都是「读取 → 变更 → 写回」的过程，其中写回走 `vscode.workspace.fs.writeFile`（异步）。当监听器在短时间内连续触发（例如批量导入图片、一次新增多个目录）时，后一个任务会在前一个任务真正写盘之前就完成读取，拿到旧的 assets 列表，最终写回时把前一个任务的改动覆盖掉。

### 实现细节
- `writePubspec` 改为同步的 `fs.writeFileSync`，写回在任务内即刻完成，不再留下未落盘的窗口；调用方不再需要 `await`。
- 新增私有静态串行队列 `opQueue` 与 `enqueue()`：所有修改类操作统一排队执行，保证「读-改-写」的原子性。队列在任务失败时吞掉 rejection 继续跑下一个任务，而任务自身的错误仍通过返回的 Promise 抛给调用方。

## 一键删除选中的单个或多个图片及其所有变体

### 需求描述
在资源管理器中选中一张或多张图片，右键即可删除这些图片，同时删除它们在变体目录（`1.5x`、`2.0x`、`3.0x`、`4.0x` 等）下的同名图片。

### 实现细节
- 入口：`Flutter` 子菜单（`flutterDevTools.explorerContext`）新增命令「删除图片及所有变体」，仅在图片扩展名（png/jpg/jpeg/webp/gif/svg/bmp）时出现；命令同时接收 VS Code 传入的 `uri` 与 `uris`，支持多选。
- 变体识别：`ImageVariantUtils` 按 Flutter 约定处理，变体目录是图片所在目录的直接子目录（目录名匹配 `^\d+(\.\d+)?x$`）。
  - `getBaseDir()`：选中文件若位于变体目录内，则回退到其父目录作为基准目录。
  - `collectVariants()`：在基准目录及其变体子目录中收集**同名且同扩展名**的图片，返回去重后的绝对路径列表。
- 删除方式：`vscode.workspace.fs.delete(uri, { useTrash: true })` 移入系统废纸篓，误删可恢复；删除前弹窗列出将被删除的文件（超过 12 个折叠为「…等 N 个文件」）。
- 引用清理：不在本命令内直接改 `images.dart`，删除文件会触发已有的 `ImageAssetWatcher`，由它在确认所有变体都已消失后自动移除 `Images` 中的 getter 方法，行为与手动删除文件保持一致。

### 补充：图片身份包含扩展名
`foo.png` 与 `foo.webp` 是两张不同的图片，只删其一不会影响另一张的变体。因此需要同时删除它们时，要在资源管理器里把两个文件都选中。
由于 `Images` 的 getter 方法名忽略扩展名（两者同名会共用一个 getter），只删 `foo.png` 时反而会把这个共用 getter 一起删掉——`foo.png` 的变体已全部消失，而 getter 记录的路径正是 `foo.png`，`foo.webp` 保不住它（实际行为，见「移除图片引用前先剔除所有失效引用」一条）。此时若还需要在 Dart 里引用 `foo.webp`，重新生成一次引用即可，或把两个文件一起删除后按需要重建。

## 修复图片 doc hover 中链接与图片无法展示

### 问题描述
在 Dart 代码中 hover `Images.xxx` 时，浮层里的文件超链接和图片预览都显示不出来。

### 原因分析
`src/provider/image-doc-hover-provider.ts` 用绝对路径拼接 markdown：

```ts
imagePath = pathUtils.join(workspaceFsPtah, relPath);
openPath = pathUtils.join(workspaceFsPtah, element);
```

存在一个问题：

1. 裸路径（无论绝对还是相对）在 markdown 中不做 URL 编码，项目路径含空格（如 `ide plugin`）时会被 markdown 解析成「链接目标 + title」，Windows 下反斜杠还会被当作转义字符。

### 实现细节
- 直接使用 `vscode.Uri.file(绝对路径).toString()` 生成 `file://` URI，由 VS Code 完成百分号编码与平台路径规范化。
- 为 `MarkdownString` 设置 `baseUri = document.uri`，保证相对引用也有明确的解析基准。
- 保留 `isTrusted = true`；插件在 `package.json` 中声明 `untrustedWorkspaces.supported: false`，工作区必然是受信状态，`file://` 图片可以正常渲染。

生成的 markdown 由：

```md
[assets/images/home/icon.png](Users/xxx/flutter%20demo/assets/images/home/icon.png)

![](Users/xxx/flutter%20demo/assets/images/home/icon.png)
```

修正为：

```md
[assets/images/home/icon.png](file:///Users/xxx/flutter%20demo/assets/images/home/icon.png)

![](file:///Users/xxx/flutter%20demo/assets/images/home/icon.png)
```

- `src/provider/image-doc-hover-provider.ts` (修改)
